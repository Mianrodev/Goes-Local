# QA report: 25 Sep 2026 (v15.79-shared, both cities)

How this was tested: the public pages were fetched live through an outside page fetcher (the Claude sandbox's own network can't reach the sites yet), both D1 databases were queried read-only, and `worker.js` was reviewed line by line. Nothing was changed on the live sites. Nothing behind a login (admin, /manage, forms, payments) was clicked through.

## Security (fix first)

1. **Listing takeover through the claim form.** In `/api/claim` (~9784–9829), picking the role "Manager" or "Other Employee" calls `ghlSetOwnerEmail(env, id, ownerEmail)` immediately, before any human review, using an email the claimant typed. The next sync copies GHL "owner email" into `businesses.owner_email` (norm ~1010, upsert 1795). `ownedIds()` grants /manage access purely on `owner_email`, and `/api/login/code` (8095) sends a login code to that address. So anyone can gain edit rights over any listing, including already-claimed ones, and the real owner's email is overwritten. **Fix:** only set owner email when an admin approves the claim in /admin/claims.
2. **Script injection in listing pages.** `PAGE()` (4356) writes JSON-LD as `<script type="application/ld+json">${JSON.stringify(o.ld)}</script>`. `JSON.stringify` doesn't escape `</script>`, and `BIZPAGE` (4643) puts the owner-editable name and description in it. A description containing `</script><script>…` would run on every visitor's browser (the CSP allows inline scripts). **Fix:** escape `<` as `<` in the JSON-LD output. One line, and it covers blog/news/SEO schema too.
3. Smaller: `/admin/seo/reset` deletes over GET (CSRF-able by a link); `?key=ADMIN_LOGIN_KEY` in the URL is accepted (ends up in logs/history); `safeNext` lets `/\evil.com` through (open redirect after login).

## Money

4. **Orlando can't take upgrades.** `ghlPayReady(env)` is `!!env.PAYMENT_WEBHOOK_KEY`, which Orlando doesn't set, so `/manage/upgrade` shows "Not set up yet — check back soon" while `/pricing` advertises Plus/Pro. The pay links (`FEATURED_/PREMIUM_PAY_URL*`, ~3493) are also hardcoded Miami links; if Orlando were switched on as-is, payments would go through Miami's GHL and the webhook would hit Miami's Worker, which doesn't have Orlando's listing (404). This needs Eric's decision: one merchant, or `CITY_PAY_*` variables.
5. **The payment webhook says "ok" even when the upgrade failed** (9280–9290): `ghlAddTag`/`ghlRemoveTag` don't check the response and `insertOne` returns false without throwing, so GHL never retries. A paid customer can stay un-upgraded with no error anywhere.

## Silent "success" (the known recurring pattern)

6. Claim approval (7736–7760) ignores `ghlSetOwnerEmail`'s result, marks the claim approved and emails the owner anyway, so the owner can log in to an empty dashboard.
7. `/account/profile` (8436–8452) sends native fields and `customFields` (birthdate, gender) in one PUT, the combination GHL is known to drop custom fields from.
8. "Thanks" is shown after a failed write: Add listing (9668–9689, all three `claims` INSERTs swallowed, so the submission never reaches /admin/pending), cancellation (9095), deletion request (8811), enquiry (9700–9764), review/photo/comment (9488–9538), admin custom code save (6138).
9. The pending email-invite cron (2746–2760) re-checks the same oldest 15 rows every 5 minutes; rows with no email block newer invites for up to 90 days, and every check does a full upsert plus search-index rebuild.

## Corrections to the handoff

- **5a (D1 write cost) is partly done already.** `syncStep` skips unchanged rows with a fingerprint (`FP(incTuple) === FP(priorTuple)`, 1826–1834). The remaining writes most likely come from **a full FTS5 search-index rebuild** at the end of every sync pass (1901) and in every `insertOne` call (2069–2090, run up to ~30× per cron tick through imports and invite checks). A rebuild rewrites the whole index (~17k rows on Miami) each time. Target this first.
- **5b (/blog 500):** the blog queries are all guarded; the only unguarded path is `shell()` (2299–2317), whose cache is cleared after every sync and by anyone adding `?refresh` to a URL (9391, no auth). This matches the "fails around sync" theory. Confirm with the Observability logs.
- Multi-city settings are applied correctly (no values are frozen to Miami at load time). Minor Miami leftovers: `(305) 555-0100` placeholders, "best photographer miami" admin placeholder, unused `POPULAR`, Miami-only `HOOD_ALIASES`, and Miami fallback images.

## Follow-up (same day, after v15.80–v15.81)

- **D1 cost has moved from writes to reads.** Cloudflare GraphQL `d1AnalyticsAdaptiveGroups`, 18–25 Sep: rows written are now small (Miami 36k–134k/day, Orlando 18k–123k/day; the sync fingerprint skip works). **Rows read are huge: Miami 1.8–4.0 billion/day, Orlando 0.44–1.1 billion/day** (~100 billion/month combined vs 25 billion included on Workers Paid, then $0.001 per million), so roughly $70–100/month on reads at the current rate.
- The main driver is crawler traffic on filter combinations (see changelog/v15.81.md): ~1.8k+ requests/hour per city, each running full-table-scan queries over ~15–17k listings. v15.81's robots.txt rules should stop Applebot once it re-reads robots.txt (usually within a day). The Alibaba Cloud Singapore scraper (ASN 45102) probably ignores robots.txt and needs a Cloudflare WAF block (needs Zone WAF edit on the token) or an in-code block.
- **Check on 26–27 Sep:** re-run the GraphQL query; reads should drop sharply. If they don't, add indexes for the category/filter queries and cache the filter pages.
- `/blog` errors: none in 7 days of logs; the page was just slow (1.5–2.5 s) because D1 is in Singapore. Now 0.4–0.8 s with Smart Placement + v15.81.
- Category pages are still ~3.5 s (a heavy per-request calculation) — next thing to optimise.
