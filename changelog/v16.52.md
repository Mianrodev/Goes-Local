# v16.52-shared — sales handle "needs a person" requests inside GHL

Eric, 14 Oct: "sales only works within GHL and the admin panel can only be accessed by the dev team."

## The problem

Claims and new listings that couldn't be verified with a code went "to the team": an admin email, plus Admin → Claims and Admin → Pending listings. Sales can't use either, so these requests waited forever.

## What changed (`salesHourly`, runs every hour before `bvHourly`)

1. **Duplicates close by themselves.**
   - A waiting claim or new-listing request closes when the same person already owns that business on the site. Claims become `approved` and new listings become `listed`, with a note `[closed: already live and owned by this person]`.
   - The first run on live data closes about 5 old requests in Orlando (including LJ Best's duplicate from today) and about 19 in Miami.
2. **One GHL task per business that needs a person.**
   - **Which requests:**
     - Anything handed to the team (`[to-team: …]`).
     - Any request from the last 14 days that never got a code and wasn't part of the backlog invites, once it's 30 minutes old.
     - Rows marked `[held: …]` are skipped.
   - **Where the task goes:**
     - The business contact for a claim.
     - For a new listing, the business contact, or the person's own contact if there's no business contact yet.
     - It's assigned to the contact's rep, and the contact gets the tag `needs-review`.
   - **What the task says:**
     - Who asked and why the code didn't work.
     - What to check: for a claim, call the number on the listing, not the one they gave; for a new listing, confirm it's a real local business.
     - It warns when a claim would take a listing away from its current owner.
   - **More than one request for the same business** shares the first one's task.
3. **The rep answers with a tag on that contact.**
   - `approve-request`: a claim is approved through `approveClaim` (owner set, "approved" email). A new listing is published through `publishListing` (live, "you're live" email, welcome-call task).
   - `reject-request`: the request is rejected, and "claim-request" / "pending-listing" is removed. No email goes out.
   - Each row is locked first (`verifying-…`), the same way the code flow does it, so nothing is approved twice. A failed publish goes back to waiting.
   - The tags (`approve-request`, `reject-request`, `needs-review`) are removed once nothing is left waiting on that contact.
   - These tags never show on the public site, because only the fixed LABELS list does.

The admin email and the admin queues still work as before, for the dev team.
