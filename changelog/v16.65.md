# v16.65-shared — sitemaps: real "last changed" dates, and the Best-of sitemap no longer blocked

SEO team (via Eric, 22 Oct): "Sitemap is not working and not getting updated automatically."

## What was wrong
1. `/sitemap-best.xml` (added with the Best-of pages) was never added to the Cloudflare rules' exempt paths, so any
   crawler from a cloud network (SEO tools, site auditors) got the "Just a moment…" challenge (403) instead of XML.
2. Sitemaps were always generated live, but no entry said when it changed, and the sitemap index said "now" for every
   file on every request. Search engines treat a date that always moves as meaningless, so they could not tell
   what was new.

## Fix
- Every listing, category, sub-category, blog post and news item in the sitemaps now has `<lastmod>` = when it last
  really changed (`businesses.updated_at`, newest listing in that category/sub-category, post/news `updated_at`).
- The sitemap index gives each file the date its content last changed (incl. duplicates hidden), not "now".
- `scripts/security-rules.mjs`: `/sitemap-best.xml` and `/blog-sitemap.xml` exempt from the challenge rules;
  re-applied to all 9 zones.
- Unchanged: Google is a verified bot and was never challenged; SemrushBot/AhrefsBot stay blocked on purpose
  (they were the heavy scrapers in September). If the SEO team audits with Semrush/Ahrefs, they should use the
  tool's "verify site ownership" crawler or Screaming Frog, which is allowed.

## Tests
- Local: all 7 sitemap files are valid XML with dates; 77/77 suite.

## Status
- Live on Orlando, Miami, Tampa (22 Oct); security rules re-applied to all 9 zones. Checked from outside with a normal browser agent: sitemap-best.xml 200 XML on all 3 cities and GA/NY state sites (was 403); sitemap index shows real per-file dates; listing entries carry lastmod. States get the lastmod code on their next deploy.
