# v16.46-shared — claims and new listings verify themselves with a code (no sales call)

Eric asked on 13 Oct to remove the agent calls that confirmed claims and new listings. Text and email codes are both fine.

## Claims

After the claim form, `/api/claim` sends a 6-digit code instead of the old "confirm your email, then our team reviews" email.
- **Where the code goes:**
  - By text to the business phone on the listing. The SMS goes through GHL to the listing's own contact.
  - Or by email to the business email on the listing.
  - Email comes first when the claimant's email already matches the listing (tier B); otherwise text.
- **The right code on `/verify-business`:**
  - Runs the same steps as Admin → Claims → Approve. That logic was moved into `approveClaim()`: owner email, the "claimed" and "Recently Claimed" tags, "claim-request" removed, the listing refreshed, and the "claim approved" email.
  - The claimant is logged in and sent to /account.
  - The claims row is marked approved, with "[verified by text code to ending 1234]" added to its notes.
- **Falls back to the team (old flow):**
  - The listing is already claimed (a dispute).
  - The listing has neither a phone nor an email.
  - No code could be sent.

## New listings ("Add your business")

`/api/lead` with `type=add` sends a code to the phone the owner typed (through their new or matched GHL contact) or to their email.
- **The right code:**
  - Runs the same steps as Admin → Pending listings → Publish. That logic was moved into `publishListing()`.
  - The listing goes live, the owner is linked and gets the "listing live" email, and they're logged in.
- **Stays with the team:**
  - A matched existing listing that someone else already owns.
  - A failed publish: the row keeps its error note, and the team is emailed.
- **Code limits:** at most 4 code requests per visitor per hour, and 3 per phone number per hour. This stops the form being used to text strangers.

## The code page (`/verify-business`)

- Codes last 15 minutes. After 5 wrong codes the request goes to the team. At most 5 sends per request.
- Visitors can resend, or switch between text and email when both exist.
- "Can't get the code? Send it to our team" hands it to the team. The usual admin email goes out at that point (not on submit), and a new listing's owner gets the "we've got your listing" email.
- The team still gets an email for every automatic approval or publish, marked "APPROVED/PUBLISHED AUTOMATICALLY … No action needed."

## Daily "needs a person" email

Once a day after 8am New York time, `needsHumanDigest()` runs from the hourly cron.
- It lists claims and new listings still waiting more than 30 minutes, with links to the two queues.
- It goes to the people on the "new claim" notification list. Nothing is sent when both queues are empty.

## Wording

- **Claim page:** "we'll text a 6-digit code … yours straight away" replaces "an account manager will call you". The phone field placeholder no longer says "So we can call you".
- **/add page:** the steps and FAQ now say "Verify with a code / You're live straight away". The 1–2 business days timing applies only when the code route isn't used.

## Testing

Tested on a local copy with a fake business: wrong code, right code, switching to email, "send to our team", and an expired page. `BV_TEST_ECHO=1` (local `.dev.vars` only, never set on a live site) prints the code instead of sending it. Actually sending texts and putting a listing live needs a live test.

## GHL (Eric, by hand — the GHL API can't edit workflows)

Both forms still add "pending-listing" / "claim-request" when submitted, and the code removes them about a minute later.
- The "Pending Listing" workflow (and any workflow that starts on "claim-request") should wait about 30 minutes and only continue if the tag is still there. That way only unverified ones reach a caller.

## Wording pass (same release, Eric 13 Oct: "different wording on the emails and sites")

- **/claim step 2:** "Verify with a code: we text or email a 6-digit code to the business. Enter it and it's yours instantly."
- **/add:** the headline line now says "free, verified in 30 seconds with a code, and live straight away", and the stats strip says "30 sec to go live".
- **Home trust box:** "Owner-verified: every claimed business is verified by its owner with a code…" replaces "reviewed by our team".
- **Emails:**
  - Claim approved → "You're verified — the listing is yours".
  - Listing live (both versions) → "You're live on {{brand}}".
  - The two fallback emails (we've got your listing, confirm your email) explain that the team checks the request because it couldn't be verified by code.
  - The claim invite: "is live. Create your free account in 30 seconds…", with the subject "… claim it in 30 seconds".
- **Admin → Email templates:** none of these had been edited there on any city, so the new defaults apply straight away.

## Automation pass and QA (same release, Eric 13 Oct: "no daily email, as automatic as possible, handle disputes, sales become account managers")

- **No daily "waiting for a person" email.** `needsHumanDigest` is removed.
- **Website-domain route:** a claimant whose own email is on the business's website domain (claim tier A) can get the code at that address.
- **Disputes:**
  - When someone verifies a listing that another person owns, the claims row becomes `transfer-pending`, and the current owner gets the `transfer_notice` email with a "Keep my listing" button (`/keep-listing`). The GET only shows a button; the POST acts.
  - If nobody objects within 72h, `bvHourly` moves the listing.
  - If the owner keeps it, the row becomes `disputed`, the business gets the "dispute" tag, a GHL task "Ownership dispute" goes to the contact's assigned rep, and the claimant gets the `transfer_kept` email.
  - The current owner re-verifying their own listing is approved as normal.
- **Account managers:** every approval or publish (by code or by admin) creates a GHL task "Welcome call: {business}", due tomorrow and assigned to the contact's assigned rep, plus the "welcome-call" tag.
- **Reminders:** rows that got a code (`[code-sent]`) but are still waiting 2h–7d later get one `verify_reminder` email. Its "Send me a new code" link is `/verify-business/restart`, where GET shows a button and POST sends the code.
- **Still unverified a day later:** the row goes to the team once, as a single per-item admin email.
- **Off switch:** `CITY_BV_OFF=1` in a city's Variables brings back the old team flow instantly.
- **Security, from an independent code review:**
  - Sign-in happens only when the code went to the email being signed in. A phone code approves the claim, and the sign-in link arrives by email.
  - "Add your business" with a phone that matches an existing live listing:
    - Only a text to that phone counts.
    - Nothing on the listing changes before verification.
    - Texts go only to US numbers.
  - Guesses are counted atomically in D1 (new `claims.bv_tries` column in migrate), 5 per request, plus 30 per visitor per hour.
  - Sends are 60 seconds apart, with a site-wide cap of 300 verification texts a day.
  - A double-tapped right code approves once: the row is locked as `verifying-…`, and the hourly job releases any lock older than 15 minutes.
  - Each row in the hourly job has its own error handling.
  - "Keep my listing" acts only on a row that is still `transfer-pending`.
- **QA:** `scratchpad/qa.cjs` (local `wrangler dev --test-scheduled`, `BV_TEST_ECHO=1`) runs 43 scenarios and all 43 pass. They cover the happy paths, wrong, expired and reused codes, website-domain email, the old flow when there's no channel, dispute keep and 72h transfer, owner re-verify, lockout, resend limit, double tap, XSS, the team hand-off, bad links, reminder and restart, the add rate limit, and the admin Approve button. The off switch was checked separately.
